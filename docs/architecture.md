# 数据与权限设计

## 信任边界

客户端通过 `wx.cloud.callFunction` 调用 `gameApi`，只提交动作与参数。云函数从 `cloud.getWXContext().OPENID` 生成稳定的内部玩家 ID，不使用请求里的 `userId`、`openid`、角色或房主标识认证。

OpenID 不返回客户端。所有集合拒绝客户端直连读写。即使知道牌局 ID 或邀请码，非参与者仍无法调用 `getRoom` 读取牌局。加入申请者只能读取自己的批准状态，不会收到牌局名称、成员或积分明细。

所有已加入玩家可查看**该局**的全员积分与明细；“我的牌局”根据本人 `memberships` 查询，后端再次核对房间参与关系。房主始终也是参与者。

## 集合

- `users/{userId}`：昵称、创建时间。userId 是 OpenID 的 SHA-256 摘要前 32 个十六进制字符，带 `u_` 前缀；昵称不是身份凭据。
- `rooms/{roomId}`：名称、房主、状态、邀请码、参与者映射、加入申请数组和积分事件数组。
- `invite_codes/{code}`：当前 roomId、过期时间。活动码通过事务占用，过期码可复用，不以邀请码作为历史主键。
- `memberships/{roomId}_{userId}`：用户参与关系、加入时间。只有批准加入或创建牌局才能在同一事务中写入。
- `rate_limits/{userId}_{scope}`：一分钟窗口内的操作计数。无效邀请码尝试也消耗额度。

## 状态流转

加入申请：`pending → approved / rejected / cancelled`。批准时原子写入参与者与历史关系。重复批准同一申请返回当前结果，不重复写入。

积分事件：`pending → approved / rejected`；`approved → revoked`。原记录不删除，撤销后不再计入投入总数，确认与撤销时间均保留。

`kind = add` 的已确认事件计入登记次数与投入积分。`kind = finish` 是结束时持有积分，只有该玩家的登记申请全部处理后才能提交。确认结束积分后该玩家不能继续登记；房主可先撤销结束事件，再更正登记。未登记结束积分时，积分变化为 `null`，不是零。

牌局：`open → closed`。必须先处理所有待确认积分；关闭时拒绝未处理加入申请并释放仍属于本局的邀请码。归档后保留读取权限，拒绝新加入和任何新的积分写入。

重复操作若已经成功，则允许返回相同结果，包含归档后的已成功登记重试；这不会新增或修改已归档数据。

## 并发与重试

单局变更通过数据库事务读写同一个牌局文档，云 SDK 在事务冲突时重试。创建牌局通过调用者身份加 `requestKey` 确定 roomId；积分事件通过玩家 ID 加 `requestKey` 确定事件编号。同一键传入不同内容会报错，不会静默替换原记录。

前端在网络错误后重试相同表单时复用请求键。页面审批不依赖客户端统计结果，所有次数与总数由服务端从已确认事件计算。

邀请码的占用、加入批准、积分确认、归档都在事务内重新检查状态。过期码分配给另一局后，旧局关闭或更新邀请码不会删除新局的映射。

## 本地验证的范围

业务测试用可原子提交、失败回滚的内存存储验证权限、并发请求和状态机；适配器测试核对微信 SDK 的参数形状与错误传播；页面测试通过 WCC 编译后的渲染树检查条件内容。它们未连接真实微信账号、云数据库或部署服务。

微信开发者工具的真实编译、云端事务冲突行为、集合权限和 AppID 对应的身份登录，仍需完成 README 中的部署与多账号真机测试。
